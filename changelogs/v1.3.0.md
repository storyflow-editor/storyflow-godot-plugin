##### New Features

- **Data Assets in the runtime**: `.sfd` Data Assets exported from the editor are now imported, resolved and executed. The exporter writes `data-assets.json` beside `characters.json` and the plugin builds a seed table from it at project load, keeping the full parent chain rather than flattening values onto the leaf, so setting a value on a base asset still cascades to every descendant that does not override it
- All three node types execute: `getDataAsset` (the reference pill), `getDataAssetVariable` and `setDataAssetVariable`. The pill is what binds an accessor to an asset, so two otherwise identical accessor nodes wired to two different pills read two different assets
- Reads resolve leaf to root taking the nearest session write or file override, falling back to the root-most declaration's own value. Writes go to the referenced asset's own level and land in a session overlay that never touches the imported seed, so a game reset restores authored values exactly
- Data Asset booleans gate dialogue options through the normal option-visibility path, and the array operation nodes (`addTo`, `removeFrom`, `clear`, `setArrayElement`) route into the overlay when their array input comes from a Data Asset accessor
- A binding that has gone stale degrades instead of guessing: a missing variable id, an unwired pill, a deleted asset, a variable no longer declared on the chain or a declaration whose type changed under a live node each fall back to the node's own type default and warn once per node, so a broken reference costs one log line rather than one per frame
- **Data Asset access from game code**: `get_data_asset_bool`, `get_data_asset_int`, `get_data_asset_float`, `get_data_asset_string` and `get_data_asset_enum` on `StoryFlowComponent`, each with a matching setter that reports whether the write landed, plus `get_data_asset_variant` as the untyped door for arrays and maps. An asset is addressed by its id or by its display name, and the typed accessors refuse a variable whose declared type does not match rather than answering something plausible
- **The unified save format**: save files now use the v1 state format shared with the Unreal and Unity plugins. Type codes are written as names instead of integers, which is what lets a save move between engines at all: the same integer means different types in different plugins. Records carry both an id and a name. Values are written natively instead of wrapped in per-value envelopes, and the session's Data Asset writes persist under a sparse `dataAssets` key that all four runtimes now write byte-shape-identically
- Compatibility runs one way. Every save a player already has keeps loading: the reader detects the old format by its section keys and reads it through the original code path unchanged. A save this version writes is not readable by a pre-v1.3.0 build, which looks for the old section names, finds none and restores nothing while still reporting success. Downgrading the plugin below 1.3.0 after saving is therefore not supported
- Enum value lists now travel with saved variable records, so a save carries the information an integer to enum conversion needs rather than depending on the project to supply it

##### Improvements

- `StoryFlowSaveData.save_to_slot` now takes the Data Asset seed and session overlay as two additional required arguments. The manager API is unchanged, so `save_to_slot("slot1")` and `load_from_slot("slot1")` on the `StoryFlowRuntime` autoload keep working exactly as before. Only game code calling the static `StoryFlowSaveData` helper directly is affected, and it fails loudly at the call rather than silently writing saves with no Data Asset state in them. The arguments are required rather than defaulted for that reason
- The save reader tolerates a damaged file section by section. A section of the wrong kind, an unknown type name, a record that is not an object or an entry with no key restores as nothing instead of failing the whole load, which matters because a save file is exactly the input that arrives hand edited or half synced

##### Bug Fixes

- **Character display names and portraits lost on every save**: `setCharacterVar` mutates a character's Name and Image at story time, but neither field was ever written to the save file. Loading therefore reverted both to the values the character was imported with, silently undoing any portrait swap or rename the story had performed. Both now persist and restore. A save written before this version carries neither field, and their absence is read as "keep the current ones", so loading an old save behaves exactly as it did
- **Save loading becoming permanently unavailable after a dialogue ended abnormally**: loading a save is refused while a dialogue is running, which is tracked by a count each component increments at dialogue start. Two paths took that count up without ever bringing it back down. A component freed while a dialogue was still active, which is what a scene change or a `queue_free` does, tore its state down without unregistering. Separately, starting a second script on a component that had not been stopped first took a second registration while the first was still held, and the single release on the eventual stop could only pay off one of them. Either one left the manager reporting a dialogue active forever, so every later `load_from_slot` was refused with no way to recover short of restarting the game. Each component now witnesses its own registration, releases the one it holds before taking another and gives it back on both teardown paths, exactly once
- **A project reload stranding the running dialogue on stale global variables**: `set_project`, which the editor's WebSocket sync calls on every re-import, rebound the global variable dictionary to a fresh copy. A dialogue already running holds that dictionary by reference from dialogue start, so it kept reading the orphaned copy while every later write landed in the new one. This is the same failure v1.2.3 fixed for `reset_global_variables`, surviving on the one path that had not been walked. Globals are now refilled in place here too, so a live dialogue observes a project reload instead of being split off by it
